## High-level Plan

1. We need to propagate version (txnId) to SSTable and use that for Put and then for Get and Prefix Scan. Compaction changes are also inter-related to it to ensure compacted files follow the same structure.
2. During Get and Prefix Scan, always pick the latest version for the required key or keys. Core MVCC logic for picking the latest visible version (or txnId) would be added in an upcoming PR.

## SSTable Write
This first required changing the parameter of iterator function `Iterate` in memtable from `func(key, value string)` to `func(key, value string, txnId uint64)` so that SSTable has access to txnId during writes. 

This is necessary because the `writeToFile` function in SSTable which is responsible for writing data blocks to SSTable iterates through each key of the memtable using the Iterate function.

`writeToFile` is a common function which is used in both memtable to SSTable flush writes and during compaction writes.

The structure of SSTable write changes from `[length_of_key][key][length_of_value][value]` to `[64_bit_txnId][length_of_key][key][length_of_value][value]`

## SSTable Read
We also need to extract the 64-bit txnId during SSTable read. Earlier only one value existed for a key within SSTable. Hence, as soon as we found a key, we could return the value.

Now, for the same key multiple versions could be present in a single SSTable file. And the versions would be present in ascending order. The required value is the latest version from the SSTable file for the required key.

## SSTable Prefix Scan
Similar to SSTable read, we need latest version for not just one but for each key. Earlier the logic was to have a `map[string]string`: a map for key to value. Similar to SSTable read, this was fine as we were only dealing with one instance of key in a SSTable file.

Now, `map[string]string` changes to a map of key to (value, txnId) pair: `map[string]valueTxnId`. Since we need the latest version, the logic is to update the value and txnId if a greater txnId is encountered for the same key. 

## SSTable Compaction
Similar to prefix scan, the compacted map cannot be `map[string]string`. It needs to be `map[string]valueTxnId` to ensure that compaction only keeps the latest version and drops all other.

We then also need to sort the compacted map as the map is created by compacting multiple files. Each file is sorted but the files are not sorted across each other.

### Failure Fixed While Writing New Test
**Index Offsets Bug**
Once the existing tests were passing, I had also added a test to assert that the Get is always picking latest version both with and without compaction. The compaction test: `TestSsTableGetPicksLatestTxnIdWithCompaction` started failing. The encountered error during read was `errorWhileReadingSsTableDatablock`. This clearly means that during read we tried to read some bytes which actually don't exist.

This could mean that either the require data is missing (bug in write flow) or that the required data is not being read the correct way. I had to utilise Claude to fix this bug and it turned out to be the latter. 

When we are carrying out compaction, we override in-memory variables like: `firstLevelFiles` and `indexBlocks` so that future reads utilise the compacted files and index blocks. We had missed updating the indexOffsets within the in-memory run.

```go
    st.firstLevelFiles = swappedFiles
    st.indexBlocks = swappedIndexBlocks                
    st.indexOffsets = swappedIndexOffsets  // this was missing
```

Interestingly, this bug was never found through existing tests. This was because, there were no compaction tests which had the same key being over-written. If there are way too many repeat keys, the index offset for compacted file should be much lesser than index offsets of regular file, especially now that we need to capture all the versions within a memtable. Earlier the memtable would have only kept the latest version.

Two major learnings from this are:
1. Thinking more deeply about various kind of test cases that should be added. The test should also be a bit more granular so that we can get some understanding of the root cause through the failing test.
2. Debugging such kind of issues can be quite hard. I might have taken 1 or 2 days to catch this issue without Claude. But in such cases, while debugging we can start thinking what is working and what is not working. The issue has to be within compaction logic as the equivalent without compaction test: `TestSsTableGetPicksLatestTxnIdWithoutCompaction` was working. My first inclination was that this could be due to writes happening incorrectly in compacted file. Not all Get operations were failing. Check **Offset Bugfix** heading in @part_mvcc_bugfixes.md for claude's suggested deep-dive.
