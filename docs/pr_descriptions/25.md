## Scope
Before MVCC, compaction meant only keeping the latest version of key. But after MVCC we can only delete the version which is old enough such than no transaction is reading. How can we identify if a key is old enough and no transaction is reading it?

Which transaction can see the oldest data? It is the oldest active transaction id. If the oldest active transaction id cannot see a value, no one else can. It also has the oldest active transactions snapshot.

Hence, if we change our logic to: if visible to oldest active transaction id: keep.
If not visible to oldest active transaction id: remove, we can significantly simplify our logic.

How do determine if oldest active transaction id can see a value or not?
If a txnId > oldest active transaction id, it will not be visible to oldest active transaction.
If a txnId <= oldest active transaction id, it can be visible to oldest active transaction. But if there are multiple versions present for the same key, oldest active transaction would always pick the latest one and non-active as per its snapshot. Hence, if we maintain a map of "key" to "the latest visible txnId" for oldest active txnId, we can discard all older txnIds for those keys.

Coming back to txnId > oldest active transaction id case: what keys can we delete? 

If a transaction id is greater than or equal to the oldest active transaction id, we definitely cannot delete it. This is because any upcoming transaction might need to read the specific key which is written by any of those transactions.

But if a transaction id is older than the oldest active transaction id, we can potentially delete it. The oldest active transaction id will only need the latest values for each key where txnId <= oldestActiveTxnId. So, if for each key we store what is the latest txnId < oldestActiveTxnId, we can delete the rest of the keys and txnId.

If no transaction can read it. For that, it has to be old enough. What is meant by old enough?

## Brute-force approach
Check every (key, txnId) if it is required or not. 
```
For each (key, txnId):
    Check every active transaction T:
        If T > txnId: not needed, continue
        If T contains txnId in snapshot: not needed, continue
        If there exists another version of key with txnId` where
            txnId` > txnId AND txnId` <= T.id: not needed, continue
    If reached till here:
        needed = true

Final compacted list --> All needed ones only 
```

### Why the brute force approach is problematic at scale
Checking every transaction snapshot requires acquiring lock on the transaction snapshot. This is a hot path. There can be thousands of transactions running per second. Compaction is supposed to be a slow background process and it should not be blocking the transaction snapshot variables. This also means that the transaction snapshot could be changing frequently. Mid-compaction, transactions could be getting committed and new could be getting started. This would either mean that we make compaction blocking or accept that the logic is racy. Irrespective of whether we take racy or blocking approach, we still need to acquire locks?

### How can we avoid looping through every transaction?
As of now, we are check for each (key, txnId) if any transaction id needs it. We can do one simplification. Instead of checking for all transaction, let's just check if the oldest active transaction needs it. Let's call it minActiveId. 

If minActiveId needs a (key, txnId), other ongoing or upcoming transactions can also need it. 
minActiveId just needs all (key, txnId) where txnId <= minActiveId and for those txnId, only keep the latest value. This helps us drop all old values, if minActiveId doesn't need a value, not other transaction can need it.

But minActiveId doesn't need any txnId > minActiveId. What do we do with those higher txnId? There might be cases where those are needed but that would require checking every transactionId which would affect the performance. Alternatively, we can keep those (key, txnId) for now and they can get wiped out in a future turn when a newer txnId becomes minActiveId. 

What are the pros and cons with delaying the delete?
Pros: Compaction process is faster by the multiple at which transactions are running concurrently. In a high-scale it can be 1-10k transactions which are running parallely. So that is 1-10k X better transactions.
Cons: If a transaction is long-running in nature, larger amount of data would continue to stay there even after compaction. Not only that, the work also increases for specific compaction batches leading to work being spiky instead of constant. Hence, it is advisable to have shorter running transactions.

### Implementation Details
If txnId <= minActiveId, we need to only keep the largest txnId <= minActiveId for each key. We can maintain a key to (value, txnId) map for that.

We need to find the oldest active txnId during compaction start. Even that txnId might be done by the time we are done with compaction but this is still fine as the remove (key, txnId) were not needed anyway.
